# IM 重复消息修复与双账号回归

## 原因与修复

- 同一消息同时经 POST 响应与 `im:message:new` 推送抵达，前端原来直接追加，导致发送端出现两个相同 ID 的气泡。按持久消息 ID 去重，保留不同 ID 的相同文本。
- 发送入口增加同步 ref 锁，防止 React 更新按钮状态之前重复按 Enter；中文输入法确认候选不触发发送。
- 历史加载与实时推送合并，避免慢历史覆盖刚收到的消息；切换会话立即清空消息，旧会话发送响应不能写入新会话。
- 发送期间保留新输入草稿；发送失败显示提示。协作组及其他底座能力不回退。
- 按上一轮要求，仅移除侧边栏计费分组；账单路由和服务保留。

## 已运行验证

- Web 测试 5/5：HTTP/WS 任意先后顺序去重、历史与实时合并、会话切换迟到响应、连续 Enter、输入法确认；另含已有两项租户状态回归。
- 修改文件 ESLint 通过，Web TypeScript `tsc --noEmit` 通过。
- 两个独立合成账号 `owner@acme.dev` 与 `admin@acme.dev`，通过临时 SSH 通道连接已运行的生产 API 和 WebSocket，各自持有独立 token。
- 双方创建同一私聊返回同一会话；A→B、B→A 各发送一条带唯一测试标记的文本；两端分别只收到一次对应消息事件，双方历史各只有一份；标记已读后未读数为零。共 6 项通过。
- 仅写入两条合成测试消息，未清空任何历史聊天。临时结果位于忽略目录 `.test-runs/im-two-accounts-result.json`。

## 边界

双账号结果是实际服务协议测试，并非两个隔离浏览器窗口的视觉验收。前端合并逻辑由回归测试验证；这不能替代图片／文件、断网重连、大量历史分页等后续验收。部署后浏览器结果须另行记录，不以本文件预先宣称通过。
